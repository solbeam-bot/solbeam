Status

Where the proof of concept has got to — what has been proven, and what has not.

Implementation plan

✔ Phase 0 · Environment Complete
  • One x86_64 VM, provisioned by a single script. doctor reports 19 passing, 0 failing.
  • SV Node v1.1.1 in regtest, Rust, Solana CLI 4.1.2, Anchor and solana-test-validator — all installed and running.
✔ Phase 1A · Peg-in, BSV side Complete
  • A BSV deposit produces a portable mint instruction: 202 bytes, byte-identical on every run, verifiable from the file alone.
  • 48 tests, including tampered proofs, inflated amounts, replays, malformed deposits, and a chain reorg that discards a deposit.
  • Needs no node — a generated chain — so it runs anywhere.
✔ Phase 1B · Against a real SV Node Complete
  • Every byte format matched the node: transaction id, transaction codec, block header, Merkle root and Merkle branch.
  • 21 live checks. The node's raw response is committed, so the format is a fact in the repository rather than something someone remembers.
◐ Phase 2 · Solana token and light client In progress
  • Done: the light client on-chain. A checkpoint, a rolling 48-hour window (288 blocks, sized by time rather than picked), storing a bare block hash per header, with linkage and proof of work. 17 tests passing against the Phase 1A fixture, including a full mint and a hostile-advancer suite.
  • Done: the two implementations agree. The on-chain client derives the same header hash as the Phase 1A Python reference, from the same fixture, unmodified.
  • Done: a hostile advancer cannot reorder, replay or rewind. The worst it can do is stall, which is what the design claims.
  • Done: the client follows a legitimate reorg. A competing branch is staged and committed only if it is strictly heavier, so a tie keeps the incumbent. Already-minted deposits are not reversed — the twelve-confirmation depth is the protection, and the token has no freeze authority, so a reversal is impossible by design rather than merely unimplemented.
  • An adversarial review found four critical defects, now fixed. The most serious: the difficulty target was read from the header being checked, so proof of work was vacuous — anyone could append headers and mint with no hashpower. Also fixed: an unauthenticated path that let any key rewrite the trusted checkpoint or halt minting; a counterfeit mint that could strand a user's deposit permanently; and a replay key that double-minted a deposit after a reorg. Each has a test. Three critical issues remain open and are documented rather than hidden: the staking buffer is not verifiable on-chain, the program upgrade authority can override every parameter, and the reserve address is a plain key rather than a covenant.
  • Done: the deposit verifier. It consumes the fixture's 202-byte instruction — Merkle fold, on-chain transaction parsing, exact output script, confirmation depth, and replay refusal. It accepts the real deposit and refuses four tampered versions of it.
  • Done: the mint. A verified deposit mints solBSV to the address named in the OP_RETURN. The test asserts the recipient's balance equals the deposit exactly — eight decimals, one base unit per satoshi, no scaling. The token has no freeze authority and its mint authority is a program PDA, so no operator key can create supply.
  • Left: solBSV as a classic SPL token — 8 decimals, no freeze authority.
  • Left, and it is a real gap: the client is safe against a hostile advancer but cannot follow a legitimate reorg — it stalls on the abandoned branch. Closing it is a design decision as much as code, so it is deliberately not guessed at.
✘ Phase 3 · Peg-out Not started
  • Designed, not built. Burn → a bonded relayer pays BSV → the payout is proved on-chain → settled.
  • Two gates each way. Minted solBSV lands in a program-owned vault and is released only once its deposit is still canonical after a maturity window — and burned if a reorg is followed first. That makes a reorg reversible without a freeze authority and without trusting anyone.
  • Stakers on both sides, paid in what they stake — earn BSV for BSV, solBSV for solBSV. They underwrite the system, so a fraudulent mint lands on volunteers rather than diluting every holder.
  • No oracles. Reorg depth and block time come from the BSV headers; deadlines come from Solana slots.
✘ Phase 5 · Public monitoring Plan only
  • The absolute cost to rewrite the BSV chain, and how much SHA-256 is actually available to rent.
  • Reserve against supply. The protocol cannot check this — the reserve is off-chain BSV — so it is published instead, as a number anyone can verify for themselves.
  • Observed block spacing, so a chain mining far faster than its target is visible to everyone.

What is proven so far

13 adversarial plays 17 on-chain tests 21 live SV Node checks all passing

What is not proven

  • Nothing has run on a public network. The light client and the token are built and tested against a local Solana validator — Solana's regtest — and nothing more. Testnet is a later step, done with a team.
  • Redemption is not built. It is the trust-minimised half, and the hardest part — see the trust model in the documentation.
  • Nothing is independently audited. The four critical defects above were found by an adversarial review run against our own code, which is not the same thing as an audit by someone with no stake in the answer.

This page is temporary. It exists so a small group can see exactly what is real — every claim above is a test you can run yourself from the repository. It will be removed before any wider release.
